# Archived Article Deletion Implementation Plan

**Goal:** Let eligible administrators permanently delete an archived article immediately, with explicit confirmation, retained audit identifiers and safe eventual media cleanup.

**Basis:** [Phase 4 design](../specs/2026-11-01-editorial-workflow-design.md), [Task 15](2026-10-29-phase-four-editorial-controls.md), and the owner's decisions: no archive waiting period; delete revisions with the article; keep audit events with article and actor IDs and preserve Auth accounts; remove image objects only after verifying no retained references.

## Design and acceptance criteria

- Authorize only an eligible active administrator; require the article ID, expected version, a fresh request UUID and an explicit confirmation in the dashboard. Enforce archived status and expected version after acquiring the same actor and article locks used by restore. Anonymous, author, inactive and ineligible callers fail closed. An article can be deleted immediately after it is archived, with no artificial retention interval.
- Delete only the selected article, its article categories, tags, credits, main/body image links, revisions and their media-reference rows. Preserve Auth users, memberships, profiles, and all pre-existing audit events. Atomically record a single `article.deleted` audit event with surviving article UUID, actor UUID and request correlation; never include body or arbitrary data. Preserve unrelated articles, assets and historical references.
- Preserve the deleted article’s public slug in a permanent reservation and hold the existing slug-allocation lock through reservation and deletion, and make allocation consult reservations under that same lock. A deleted URL must not silently become an unrelated article; test concurrent deletion/allocation.
- Existing media-write receipts have a restrictive article FK. Preserve request-ID replay protection without retaining article content; resolve that FK explicitly and prove old requests cannot recreate deleted content. Keep existing draft/lifecycle receipts as tombstones.
- Acquire the shared advisory transaction lock `72300320261107` before actor, homepage and article locks, matching curation writes; check homepage version overflow before incrementing. Existing media finalization takes asset then article locks. Deletion must acquire asset locks with NOWAIT and roll back every change on contention; never hold a database transaction across Storage HTTP. Test actual finalization/deletion interleavings and deadlock-free failure.
- Homepage selections use a restrictive FK even after an article is archived. Lock the singleton in the same order as the homepage save, remove only this article's selection in the delete transaction and advance the homepage edit version and record a bounded `homepage.updated` audit event when changed. This prevents stale curation overwriting the cleanup; reserve/fallback logic fills the gap. Include both homepage-save/deletion lock orders in concurrency tests.
- Owner decision: remove the article immediately while retaining a permanent private ledger of its image object keys and repeatedly sweeping those exact keys. Storage and SQL cannot commit atomically. Never claim a terminal cleanup guarantee: a previously accepted upload can finish late, so even apparently absent keys remain in the ledger and are checked again. The sweeper must be bounded and fair across the entire growing ledger, retry failures, and keep work recoverable after process restart or administrator revocation. Any current administrator can trigger a retry; a protected Vercel scheduled job handles recurring sweeps. Provide clear status and operational alerts for stale/failed runs.
- Before deleting an article, atomically reserve every historical object key permanently and transfer its exact keys into the cleanup ledger while removing article-owned links, revisions and metadata. A permanent unique key registry binds every object key to immutable asset/article IDs, backfills existing assets and rejects any reuse or key mutation through database triggers. Acquire a table lock so the registry backfill and trigger installation are one atomic cutover. Every asset deletion, including ordinary unused-image removal, retires its key and adds a permanent sweep row. Synthetic test cleanup may remove only its own fixture rows. Verify no retained references can reach a ledger key and protect the check against races. Do not release uploading claims or infer quiescence from finalized status, a timeout, or a database lock. Object removal must use the Supabase Storage API, never SQL deletion from Storage metadata. Keep object keys and service credentials off the browser.
- Preserve a permanent tombstone for every deleted article ID and reject its reuse. Backfill tombstones from prior deletion receipts so earlier no-media deletions also receive prefix scans. In addition to known keys, periodically list each deleted article UUID prefix to discover objects whose old metadata disappeared before this migration or whose upload finishes late. Before deleting any discovered object, atomically register its exact key as retired only if no live asset or retained reference owns it; a unique registry prevents concurrent reuse. Use bounded, fair, resumable prefix scans with a persisted cursor and repeated full cycles; a later key before the cursor must appear in a subsequent cycle. Test deletion while paging and backlog fairness; never delete a key whose ownership cannot be verified.
- The server-side sweeper accepts no caller-supplied bucket/key. It atomically claims bounded batches ordered by least-recent attempt, advances attempt timestamps even on failure, and uses expiring claim tokens recoverable after crashes; no ledger row is removed. Monitor oldest unattempted or failed work, and do not claim eventual erasure unless sweep capacity exceeds arrivals and in-flight uploads eventually terminate. A protected scheduled endpoint fails closed without a secret and runs only on the production deployment. An administrator retry checks current admin eligibility independently; scheduled cleanup instead requires the cron secret. Service-only completion verifies a server-held claim token and exact ledger identity, and never accepts arbitrary object keys from the browser. Deletion receipts survive deleted articles; exact retries recheck current eligibility and return the original result without duplicate audit or ledger effects. Admin-facing UI distinguishes article deletion from ongoing media monitoring and never promises terminal erasure.
- Keep direct article/history/media deletion and cleanup-table access closed to application roles. Limit user-scoped RPC input and result envelopes; no arbitrary object keys from callers. A cleanup completion function must be service-only and verify the unguessable claim token and expected ledger identity; cron and admin authorization occur separately at their server entry points. Persist a visible administrator list of outstanding cleanup items, and display partial success distinctly from deletion failure. Never claim cleanup completed on an uncertain Storage response.
- All structural changes are additive forward migrations, preserving old content and retained history outside the selected article. Rollback the application by disabling new controls while keeping receipts and outstanding cleanup records; permanent deletion itself is irreversible. Public redirects, retention policies for accounts or audit events, and destructive production operations are outside this task.

## Pre-migration review findings

The independent review identified permanent-upload claims without writer-liveness proof, opposite media lock order, restrictive media-write receipts, homepage lock ordering/version overflow and deleted-slug reuse. A timeout or DB-only lease cannot prove a service-role Storage upload has stopped. The reviewed no-media slice initially blocked assets and receipts. The owner subsequently chose a permanent sweep ledger; the implemented media slice handles all asset states while preserving receipts. Final hosted verification and human review remain pending. Expose `article.deleted` in the existing safe administrator audit reader and UI; retain original draft receipts to prevent old create retries from resurrecting deleted articles.

## External interface constraints

- [Supabase Storage deletion](https://supabase.com/docs/guides/storage/management/delete-objects) must use the Storage API rather than deleting metadata with SQL. Vercel scheduled jobs run on production deployments; use a daily schedule compatible with Hobby, configure an authenticated cron secret before launch, and monitor execution. [Vercel cron limits](https://vercel.com/docs/schedules/cron-jobs/usage-and-pricing) allow Hobby jobs once daily with approximate timing.
